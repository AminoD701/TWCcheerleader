## 使用者指示與交付狀態

使用者已要求繼續交由 Codex 執行網站架構重構，並提出 APP 需要底部功能方便操作。本文件將底部導覽列為本次重構的必要交付，與 `docs/architecture-pwa-refactor-plan.md` 一起執行，不是另起一個新 APP。

本次文件提交不代表導覽已實作，也不代表 Codex 已接單；執行狀態以 PR 的 Codex 回覆與實際程式提交為準。仍維持獨立分支、Draft PR、人工驗收，不直接合併 main 或改動正式站。

## 目標與資訊架構

讓手機使用者不必捲回頁首就能切換主要功能。一般手機瀏覽器與已安裝的 standalone PWA 使用同一套底部導覽、路由與狀態，不能分別複製業務邏輯。

以下五個入口是本次建議的起始資訊架構，並非經流量統計驗證的既有使用排名。實作前核對現有全部功能及 mode 映射；若需調整名稱或分組，說明理由，不刪除功能。

| 底部標籤 | 功能範圍 | 互動要求 |
| --- | --- | --- |
| 女孩 | 女孩圖鑑、球隊、搜尋、篩選、個人頁 | 個人頁返回需恢復原列表的篩選及捲動位置 |
| 行程 | 公開活動、日期與女孩篩選、活動詳情 | 不得與「我的行程」混淆；維持現有公開行程深連結 |
| 班表 | 應援班表；以區內切換提供比賽賽程入口 | 明確區分「應援班表／比賽賽程」，保留既有賽事網址、球隊與聯盟篩選 |
| 我的 | 收藏女孩、我的行程、現有護照與本命球隊偏好 | 整合既有本機個人化資料；不得為此強制新增帳號或登入系統 |
| 更多 | 最新消息、投票、遊戲、夢幻隊伍、經紀資訊、意見回饋及其他現有次要入口 | 建立分組清楚的功能頁；保留全部既有入口及相容網址，不做無作用按鈕 |

上面是功能分組而非保證目前已有對應路由。所有現有 mode/query/hash 必須先盤點，再以相容映射接入新導覽。首頁是否有獨立 landing 流程需一併處理，不能讓初始載入畫面被導覽遮住或出現未初始化操作。

## 共用架構要求

- 定義唯一 navigation config，集中標籤、SVG icon、目的地與父層歸屬。桌面頂部/側邊導覽及手機底部導覽從同一設定與路由狀態生成。
- 響應式呈現以可用視窗寬度決定，不能只用 user agent 或 standalone 判斷。手機瀏覽器也要受益，寬螢幕 PWA 則可以用桌面導覽。
- 手機頂部保留品牌、頁面標題、搜尋或情境操作，不再同時保留另一整排重複主導覽。桌面不得同時出現兩套互相競爭的主導覽。
- 以模組/元件和受控樣式實作，禁止在 index.html 尾端追加大量 inline CSS/JS、反覆覆寫 window.setMode，或複製所有功能程式成 app-mobile.js。
- 暫時銜接舊 setMode 時可用小型 adapter，但需列明移除條件與測試，不能成為新的永久補丁堆疊。

## 導覽行為

- 五個入口均使用「圖示＋短文字」，未選中項也保留標籤；選中狀態不能只靠顏色。
- 底部列提供持續可用的主要切換，不因一般上下捲動頻繁消失；完整模態視窗開啟時，底部導覽不得蓋在模態視窗上或仍可被背景點擊/鍵盤操作。
- 每個主區保留自己的搜尋、篩選、月曆日期和捲動位置；切換回來不要把使用者送回預設狀態。
- 個人页或活動詳情能依進入來源返回；從「行程」進入女孩詳情時，不能無條件把父層歸屬及返回目標改成「女孩」。
- 導覽狀態、網址、瀏覽器上一頁/下一頁與 APP 內返回必須一致；重複點目前入口不增加無限重複歷史，也不重複註冊事件或無必要重新抓取全部資料。
- 保留 `/TWCcheerleader/` 子路徑、現有 PWA identity/scope/start_url、`?mode=events`、`?mode=news` 與其餘盤點到的舊深連結。直接開啟與重新整理不能 404 或回錯區。
- 最新消息等放入「更多」的子頁，仍可從舊網址直接開啟，底部父層狀態需正確。

## 版面、觸控與可及性

- 本專案觸控目標採至少 48 x 48 CSS px；此為專案設計目標，不宣稱與平台原生 dp/pt 單位完全相同。320–430 CSS px 寬度均需容得下五個標籤，不得依賴橫向捲動。
- 底部列納入 `env(safe-area-inset-bottom, 0px)`，適當設定 viewport-fit，保留使用者放大功能；頁面末端、浮動按鈕、toast 及安裝提示須預留導覽實際高度加安全區，避免最後一筆資料或按鈕被遮住。
- 移動既有右下角 PWA 安裝按鈕，或整合到「更多」的安裝區；已安裝不再顯示多餘安裝 CTA。不得讓既有浮動工具按鈕與新導覽互相遮挡。
- 支援動態瀏覽器工具列、直向/橫向、軟鍵盤及 visual viewport 變化。鍵盤開啟時可暫時隱藏底部列，但不能遮住輸入框/送出鍵，關閉後須恢復；不要把硬體鍵盤焦點或單純旋轉誤判成軟鍵盤。
- 採清楚背景、分隔與一致的品牌色，不為導覽加入高成本持續動畫。支援 reduced motion。
- 跨頁導覽使用語意化 nav 與合適的 link，提供可讀名稱、可見鍵盤焦點及正確 aria-current；不要只因外觀像 tabs 就對跨頁連結濫用 tablist 角色。
- 若「更多」採模態 sheet 而非獨立頁面，必须額外做好 dialog 語意、背景 inert、焦點圈限、Escape/返回關閉與焦點還原；預設優先採較易維護的獨立功能頁。

## 與 PWA 重構一起驗收

本需求不取代原始計畫中的快取隔離、no-store、安裝失敗、離線、更新提示與儲存資料保護。新底部導覽必須納入 app shell 及版本策略，避免新 HTML/舊 JS 混用。

沒有網路時，已載入的收藏及可用本機內容仍應可操作；未快取的目的地提供清楚離線說明，不能白屏、假裝沒有資料或清除使用者資料。新版本更新不能把目前未完成輸入或收藏清空。

## 最低驗收案例與交付證據

1. 在 320、360、390、430、768、1366 CSS px 及手機橫向檢查；小螢幕底部列、較寬畫面頂部/側邊導覽正確切換，且無重複主導覽與橫向溢出。
2. 五個入口都導向實際功能；全部原有功能有可發現的入口，最新消息/投票/遊戲不得失蹤。
3. 女孩篩選列表 → 詳情 → 返回，以及活動 → 女孩詳情 → 返回，篩選、日期與捲動位置保持正確；跨主區切換也能恢復。
4. 比賽賽程和應援班表各自保留資料與選取狀態；收藏/我的行程跨刷新保留，舊資料仍可使用。
5. 瀏覽器上一頁/下一頁、APP 內返回、直接深連結、重新整理，以及 events/news PWA shortcuts 都正確。
6. 頁面最後一張卡片、模態底部操作、表單送出、toast、安裝/更新提示、原浮動按鈕不被底部列遮住；捲動時不產生無法關閉的疊層。
7. 軟鍵盤、iPhone 安全區、Android 返回、文字放大及鍵盤/螢幕閱讀器基礎操作分項記錄。瀏覽器自動化不能替代已安裝 PWA 真機驗證；無法執行的項目明確標示未驗證。
8. 提供同一畫面的手機/桌面前後截圖、實際程式變更、單元/整合測試和可行的 e2e 結果，以及已完成/未完成清單。文件提交或靜態截圖不算底部導覽功能完成。

## 實作優先順序

先完成原計畫必要的資料/PWA安全修正與最小共用導覽基礎，接著在第一個可操作的手機預覽中交付底部導覽、既有頁面相容 adapter、返回狀態與測試。其餘功能模組按原計畫分階段遷移。不要把底部導覽無限延後到所有重構都完成後，也不要只貼五個按鈕就跳過架構工作。
